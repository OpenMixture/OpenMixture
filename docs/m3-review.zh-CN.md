# M3 评审与 M4 进入决策

[English](./m3-review.md) | 简体中文

**评审源码：** `e9dd03b`（PR-010），2026-09-08。三种材质均获用户接受，并具备通过的本地 Metal／固定 SwiftShader 证据。以下回答 [PR-010 之后](../INITIAL_PRS.zh-CN.md#pr-010-之后)要求的六个问题。据此编写的 [M4 实施计划](../M4_PRS.zh-CN.md)仍为计划；本次评审没有实现其中的运行时变更。

按用户要求，远端干净检出／Linux CI 继续暂缓。本地材质验收不关闭这些平台验收项，也不代表获准发布。目录保持十一种节点；本次评审不放宽第十三节点停止规则。

## 1. 三种材质是否真正得到人工接受？

**是，限于当前接受的观感目标。** 用户在查看受控 PBR 对比后，接受了[陶瓷](../fixtures/materials/glazed-ceramic/reports/human-review.json)、[皮革](../fixtures/materials/leather/reports/human-review.json)和[木材](../fixtures/materials/wood/reports/human-review.json)。这些决定绑定到记录的清单和 PBR 证据，并非从机器评分推断。较早的 PBR 采集保留历史 pending 标签，也不声称自身完成人工验收。

[验收回执](./reviews/m3/acceptance.json)核验这些绑定并汇总最终本地报告：三种材质共十一个 1K 用例，每个四通道，两种适配器策略均通过。软件比较要求逐像素精确一致。硬件使用各材质声明的容差；木材有文档依据的最大两个字节等级差异及受限变化像素比例保持不变。范围、接缝、空间／方向变化、参数因果和高度／法线关系继续使用原有门禁。本次评审未重新生成接受的源码或像素。

这证明三个限定材质目标已获接受，不代表任意场景下的照片级真实感或更广节点词汇已获验证。

## 2. 其他开发者能否理解公开 `.mix` 词汇？

**借助公开指南可以；尚无独立易用性研究。** [格式](./file-format.zh-CN.md)、[十一种节点契约](./node-contracts.zh-CN.md)和材质文档明确规定版本、类型化端口、参数默认值／范围、显式种子、坐标约定、平铺限制、公开覆盖及输出编码。验证会拒绝不支持的数据，不会修复后继续。公开的 `BUILT_INS` 和 `node_contract` 已提供可序列化目录，因此无需第二套目录／schema API。

[独立 Cargo 探针](./reviews/m3/native-consumer/README.zh-CN.md)拥有自己的输入，使用公开导入成功完成解码、验证、覆盖和编译。这是开发证据，并非面向陌生用户的研究。仍有两处 Rustdoc 过时：core 介绍声称六种契约，`MaterialDocument::validate` 将编译描述为未来工作。PR-011 修正文案，并将依赖仓库相对路径的文档示例替换为消费者可用的示例。

## 3. 诊断能否帮助修复图和 GPU 配置？

**JSON 诊断和 `doctor` 提供必要上下文；人类可读输出存在明确缺陷。** [十六个 CPU 探针](./reviews/m3/diagnostics/README.zh-CN.md)保留 help／usage、格式／图错误、覆盖、限额、I/O 以及显式禁用 GPU 获取的 stdout、stderr 和退出码。图／请求失败返回 `2`，I/O／获取失败返回 `1`。JSON 保留节点／端口／参数标识、测量证据和建议。[已记录的健康适配器证据](../fixtures/materials/wood/reports/README.zh-CN.md)单独覆盖实际 GPU 配置；禁用后端探针不模拟设备失败。

对于缺少必填输入的 warp，人类可读 `validate` 标明 `displacement`，而 `inspect --plan` 和 `render` 遗漏端口。它们的 JSON 仍保留端口。PR-012 必须让三个命令的人类可读报告保留同等上下文，并在两种输出模式下测试同一无效夹具。此缺口不能被默认为 SDK 已就绪。

运行时设备丢失和内存不足分类仍属于 M4。现有分阶段错误保留驱动证据，但尚未稳定地区分这两种失败原因。PR-013 负责该契约。

## 4. 1K 性能是否支持交互式消费者？

**在实测主机上支持防抖预览流程；尚未证明能连续逐帧交互。** 本次使用 `--release --locked --all-features` 构建的优化 CLI，顺序启动独立进程，输出 1024×1024，每种工作负载测三次。计时结束后解码每张请求 PNG，与接受的基准比较。Metal 输出通过各自容差；SwiftShader 木材精确匹配。完整命令、二进制／源码哈希、适配器报告及原始输出见[性能证据](./reviews/m3/README.zh-CN.md)。

| 适配器／工作负载 | Pass 数 | 完整 CLI 中位耗时 ms | 实测最小–最大 ms | Renderer 中位耗时 ms |
|---|---:|---:|---:|---:|
| Apple M5 / Metal，陶瓷，四通道 | 8 | 62.6 | 60.0–237.0 | 32.7 |
| Apple M5 / Metal，皮革，四通道 | 5 | 714.4 | 710.5–896.6 | 41.5 |
| Apple M5 / Metal，木材，四通道 | 8 | 408.2 | 401.5–604.3 | 38.7 |
| Apple M5 / Metal，粗木纹，四通道 | 8 | 340.5 | 338.9–361.6 | 41.3 |
| Apple M5 / Metal，木材，仅 baseColor | 6 | 160.6 | 158.6–162.7 | 19.9 |
| 固定 SwiftShader / Vulkan，木材，四通道 | 8 | 623.9 | 618.6–633.2 | 232.9 |

完整 CLI 耗时包括进程启动／退出、解码／编译、GPU 获取、执行、回读、PNG 编码／写入及 JSON。`Renderer` 时间不含 CLI 编码和 GPU 上下文获取，包含 CPU 准备／等待及回读转换。这些是墙钟时间，不是 GPU 时间戳。各列中位数独立计算。首个陶瓷／皮革／木材 Metal 样本包含 177–204 ms 的管线创建；没有丢弃预热或较慢样本。各进程的 Mixture 缓存全新，但 OS／驱动缓存可能已有数据。单机三个样本不能作为 p95、跨平台 SLO 或每次首次启动的承诺。

最小 `--version` 调用中位耗时在 Metal 测量中为 3.1 ms，在软件测量中为 6.3 ms。它是最小调用开销的参考，不是单独隔离出的渲染启动耗时。现有证据不能支持因进程启动而引入 N-API、守护进程或 IPC。皮革／木材完整 CLI 与 renderer 耗时的较大差距，让下一次测量应关注 CLI 配置／编码开销，以及返回自有像素的公开 Rust 消费者。这个差距本身不能单独归因于 PNG 编码，也不足以引入着色器／资源优化器。

因此 PR-011 从现有公开 Rust 路径开始。如果后续需要 Node.js 消费者，先调用已构建 CLI。PR-014 增加请求代次及过期结果拒绝，避免较慢的旧结果替换最新预览。只请求必要通道已经能减少工作，木材的六 pass 结果证明了这一点。本次评审不凭空新增性能阈值。

## 5. 2K 内存能否用简单生命周期模型约束？

**可以，限于实测工作负载和描述符预算。** 留存的 [Metal](../fixtures/materials/wood/reports/2k/metal/trace.json) 与 [SwiftShader](../fixtures/materials/wood/reports/2k/software/trace.json) 跟踪均按预计峰值内存从十一个候选中选出 `wood/default`，不是按耗时选择。在 2048×2048、四通道、八个 pass 下：

| 项目 | 字节 |
|---|---:|
| Pass 纹理 | 268,435,456 |
| Uniform 缓冲区 | 224 |
| 一个存活 staging 缓冲区 | 33,554,432 |
| 存活描述符峰值，估算与分配一致 | 301,990,112（约 288 MiB） |
| 允许峰值 | 536,870,912（512 MiB） |
| 累计分配与释放字节 | 402,653,408 |
| 渲染结束后存活／复用字节 | 0 / 0 |

保留所有 pass 纹理／uniform 到结束，并逐次使用一个回读缓冲区，已经足够。现有证据不支持增加最后消费者释放、池化或纹理复用。统计不含驱动分配、管线／绑定组和 CPU 输出缓冲区；显式 destroy／drop 不证明 OS 立即回收物理内存。预算针对单次渲染，不是并发消费者的总上限。这些开发构建的 2K 耗时没有被用作 release 交互测量。

## 6. 独立原生消费者实际需要哪个 API？

**现有公开路径足够支持首个消费者。** 它需要 `MaterialDocument::decode`、验证、`CompileRequest`／`compile`、显式 `GpuContext::request`、`Renderer::render` 及类型化诊断。结果已经提供拥有独立生命周期的 RGBA8 像素、尺寸、通道类型／编码、connected／default 来源、计划哈希、适配器、pass、耗时、分配及管线缓存证据。Core 拥有语义，wgpu 拥有像素执行，消费者拥有展示／导出和请求新旧管理。

独立 [Cargo 夹具](./reviews/m3/native-consumer/README.zh-CN.md)执行 CPU 解码／验证／覆盖／双通道编译及非法覆盖，并编译验证 GPU 获取／渲染／结果／drop 路径与原生 `Send` 约束。**它未执行 GPU 渲染，且使用源码 path 依赖，因此不算包消费者验收。** PR-011 必须在显式选择的适配器上执行公开路径，并验证 renderer 被 drop 后像素仍可使用。PR-015 必须证明打包源码在不依赖仓库相对资源的情况下可用。

承诺兼容性之前，M4 必须审查公开原始 wgpu getters、修复 CLI 诊断遗漏、定义设备丢失／OOM 行为、建立过期结果处理，并测试现有缓存的有界生命周期。这些需要形成 [PR-011 至 PR-015](../M4_PRS.zh-CN.md)，无需新的执行器、运行时 crate、绑定或编辑器。
