# ADR 0009：单次渲染临时纹理复用

[English](./0009-transient-texture-reuse.md) | 简体中文

状态：2026-09-23 通过 PR #58 接受设计。[0.8 工作实现](../perf-mat-texture-reuse.zh-CN.md)落实 Core/wgpu 原子契约；该候选的集成与完整验收仍待完成。原设计 PR 未改变可执行版本或分配行为。

## 背景

冻结的 MAT-02 默认图已经能在 1024 编译并渲染五通道。plan v2 保留其全部 23 张 pass 纹理。真实 2048 请求产生 `MIX_LIMIT_TRANSIENT_BYTES_EXCEEDED`：805,306,832 描述符字节超过不变的 536,870,912 字节上限。[保留的输入、报告及 1K 像素](../evidence/perf-mat-before/README.zh-CN.md)证明 PERF-MAT 进入条件。这是编译预算失败，并未尝试超限硬件分配。

现有计划指南明确将 v2 估算绑定到保留全部资源的分配方式。只改执行器会继续在编译阶段拒绝材质；只改估算会让执行器超过声明预算。Core 与 wgpu 必须在同一个纵向变更中实现一致的调度。

## 决策与所有权

Core 在现有依赖裁剪和稳定 pass 排序之后，为每次渲染计算确定性的物理槽映射。逻辑资源 ID、内核、uniform、节点版本、dispatch 尺寸和输出来源不变。wgpu 经现有唯一像素路径分配并执行此映射。CLI、WASM、JS 投影 Rust 契约，不计算生命周期。不增加 crate、全局池、另一执行器、pass 融合、着色器改写或重排。

设 `P` 个 pass 编号为 `0..P-1`，每个逻辑资源的最后使用先初始化为生产者 pass。遍历所有类型化输入绑定（包括重复绑定），取最大消费者索引。将每个请求输出资源固定到哨兵 `P`，包括输出别名。未请求分支已由现有裁剪移除。外部图像纹理由独立输入所有权管理，不进入此池。

按生产者 pass 顺序处理。只有槽内资源的最后使用索引**严格小于**当前 pass，才允许复用；完整 `TextureDesc` 必须相同，包括尺寸、格式与 Scalar／Color／Normal 类型，以及既有固定的单 mip、单层、单采样和 usage 策略。选择最低编号的兼容空闲槽，否则追加新槽。记录输出资源对应槽及最后使用位置。同一次 dispatch 的输入与输出不得别名。固定的输出保留到全部读回结束。

仍可在编码前创建全部物理槽及每个 pass 的 uniform。每个 pass 从映射获得输出槽及各逻辑输入槽的视图。保留现有命令编码器中的独立 compute-pass 边界，由 wgpu 排序存储写入与采样读取。复用存储时，不对排队命令引用的纹理调用 `destroy`。完成或清理时每个自有物理纹理只销毁一次。绑定组、uniform、上传图像纹理及上传缓冲保持当前显式单次渲染生命周期。不跨渲染保留纹理。

这是逻辑资源最后消费者释放与兼容存储复用，不承诺驱动即时释放或进程 RSS 降低。错误、设备丢失及销毁清理必须保留首个结构化错误并释放全部自有分配；可用上下文上的下一次渲染使用新的槽集合。

## 计划、估算与兼容性

首次实现选定 **RenderPlan v3**、哈希域 `mixture-render-plan-v3\0` 和**浏览器 API schema 3**。图 `inspect --plan` 与 `render` 外层报告改为 schema 3；doctor、固定 checker 和 asset 外层仍为 schema 1，`validate` 保持无版本。嵌套 plan／render 数据独立声明新版本。`.mix` v1、`.mixpack` v1、节点语义、原始像素编码及资源捕获／限制不变。

计划增加必需的类型化 `allocation` 对象：按物理 ID 升序的 `slots`，按逻辑资源 ID 索引的 `resourceSlots`，以及使用上述哨兵规则的 `lastUses`。槽包含完整纹理描述。Core 负责构造；序列化计划仍不能反序列化为可执行计划。根级哈希字段顺序为 `version`、`documentVersion`、`size`、`materialOutput`、`passes`、`outputs`、`allocation`、`estimates`、`imageResources`。全部调度字段参与哈希；策略上限、适配器及时间不参与。

`textureBytes` 表示已分配 pass 纹理描述符字节，改为物理槽总和；新增 `logicalTextureBytes` 表示逻辑 pass 结果字节总和，`textureCount` 表示物理 pass 槽数量。`uniformBytes`、读回布局、逐通道串行读回及外部图像计费定义保留。对于无外部资源、尺寸相同的图，设物理槽数为 `N`，`T=W*H*8`，uniform 总和 `U`，每次读回对齐字节 `R`，请求通道数 `O`：

- `textureBytes = N*T`；`logicalTextureBytes = P*T`；`textureCount = N`。
- `peakBytes = N*T + U + R`；`cumulativeBytes = N*T + U + O*R`。
- 继续保守地将所选外部图像纹理／上传暂存字节加入峰值，并保留累计／上传字段。本次不优化外部上传。
- 保留检查算术及恰好等于上限的接受边界，不提高默认值或调用方上限。

GPU 分配报告统计真实成功创建的物理纹理（包括独立上传图像）及描述符字节。`reusedBytes` 累计由已分配槽服务的 pass 结果字节，不包括槽首次使用及外部图像。uniform／staging 仍统计真实分配。成功返回时 `liveBytes=0`，释放与累计计费一致。绑定组／驱动开销及 CPU 输出仍不在描述符计费内。固定 checker 在不变报告外层下仍报告真实的单纹理分配。

首次实现检查源码／registry 版本可用性后采用下一个未发布 minor：Rust 0.8.0／browser 0.8.0-alpha.0。所有同级包版本与构建身份同步更新。消费者重新编译 Rust 并显式接受 schema 3；持久计划／哈希缓存失效，从 `.mix` 请求重新编译。不增加 v2 序列化计划加载器、双执行器或文档改写。候选消费者更新 schema 预期，旧 registry 精确消费继续固定其自身契约。历史源码／归档证据不变。本设计不改变 manifest、lockfile、wire 响应或已发布包。

## 备选方案

提高内存上限违反材质门槛，也未解决表达成本缺口。减少分辨率、通道或节点改变了目标结果。逐 pass 销毁／重分配需要更多提交及生命周期逻辑，可能增加驱动开销；单次调用固定槽保留当前编码器路径。跨类型共享可进一步减少槽，但并非必要：保守设计模拟得到 14 槽和 2K 的 503,316,944 字节，低于冻结上限。这不是实现证据。本失败不需要通用优化器、图重排、精度特化、全局池或 pass 融合。

## 交付与验证

1. **PERF-MATa：**保留真实失败及有效基线，审查本 ADR 与兼容性决策，同步架构、路线图及双语 Agent Guide，通过链接和完整仓库检查。不声明运行时实现。
2. **PERF-MATb：**一起实现 Core 调度／估算／哈希、wgpu 槽执行器及薄 schema／版本投影。不得向保留全部资源的执行器提供按复用计费的计划。链、菱形、重复输入、同 pass 排除、描述类型隔离、输出别名／固定、裁剪请求、默认输出及外部资源均需独立预期调度；验证确定性顺序／哈希、等于上限通过、低一字节拒绝及溢出检查。不能所有预期均从分配器本身推导。
3. **PERF-MATc：**同一实测适配器上证明 1K 优化前后像素精确相同、2K 五通道真实执行成功且不超过 512 MiB 和 24 pass、物理估算／计数一致、有复用且存活字节为零。覆盖多尺寸／种子／端点、部分输出、重复请求、独立 renderer、上传／包路径、失败清理及销毁后输出所有权。按冻结的 MAT-02 目标测冷／热时间并记录适配器；CPU 计划成功不足以验收。
4. 运行着色器验证（预期不改着色器）、原始及显式 v2 材质回归、Native／浏览器精确候选及包消费、相关跨运行时像素对照、六项必需检查及合并后检查。保留历史 v1 数值失败。只按明确 v3 变更更新哈希／wire 快照，不能为通过而改像素 golden。MAT-02 因果／接缝／PBR／人工验收与发布仍分别处理。

若保守映射或当前命令路径不能满足不变预算／像素门槛，保留失败并审查最小后续变化，不能隐式扩大为通用分配器或降低材质目标。
