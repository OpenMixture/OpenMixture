|---|---|---|
| 图语义 | 显式种子、确定性遍历／计划、指定端口参数、像素中心、环绕、位移场读取位置、恒等快捷路径和编码 | 不同实现的 GPU 算术逐位一致 |
| 数值执行 | f32 算术、rgba16float 中间存储、唯一 WGSL 执行器中的显式 half 舍入、有限值和范围检查 | 整个实数表达式精确计算后只做一次最终舍入 |
| 软件回归 | 记录的固定 SwiftShader 环境中，解码 RGBA8 与冻结基线精确一致，并满足独立语义／结构检查 | 普遍数学真值，或其他编译器／驱动／构建也一致 |
| 浏览器认证 | 固定候选、声明的同源码原生参照、冻结通道门槛及独立计划／结构／生命周期检查 | 原生总是更准确、所有浏览器均支持、比较失败就是 WGSL 缺陷 |
| 消费者兼容 | 源文档／节点／计划／API 边界及明确的实现和归档身份 | 仅凭 plan hash 就能确定像素 |

[比较代码](../../xtask/src/golden/pixels.rs)实际检查最大分量差、**全部四个 RGBA 分量的整体均值**以及超过 pixelThreshold 的像素比例。它记录各分量均值，但不对每个分量均值分别设门槛。当前[浏览器门槛](../browser-tolerances.json)的 pixelThreshold 为零，因此任意分量变化都计入差异像素。在 1024² 下，比例限制分别最多允许 baseColor/height 变化 10 个像素、normal 20 个、roughness 1,048 个；最大值和整体均值还必须独立通过。这是经验性的回归约束，不是感知评分、f32 误差预算或 WGSL 精度界限。即使图像看起来相同，它仍然有效。

## 正确性与兼容性判定

1. **PR15 是有独立动机的数值稳定性修正，但影响像素兼容。** 同尺寸纹理下，“整数像素＋局部位移”与原采样位置在实数意义上等价。1024×1 交替输入的见证中，2^-26 UV 位移应对应 2^-16 texel，旧绝对坐标计算丢失了该量，新实现保留了它。这证明相对理想采样存在可避免的精度损失，也支持新增回归，但不能证明旧实现违反了既有的整体表达式误差界：v1 规定 f32，却没有该误差界。新测试不能被描述成原先已经存在却失败的规范测试。[PR15 证据](../evidence/warp-local-texel/README.zh-CN.md)同时确认软件木材像素改变、冻结金图失败。
2. **PR16 是已测插值改善，不是可移植的精确性修复。** 源码 `1c65e8631c2e2bdba8fe3aaf8b7c5762c1c215f3` 的 23 个字面值用例在原生／SwiftShader 和直接 Chrome／Edge 探针上通过，缩减的浏览器 half 临界点失败消失。但相对 PR15，7 个软件木材通道各变化 1–4 个像素；冻结软件木材仍有 12/16 通道失败。实际安装包的 Chrome 仍通过 27/44，19 个完全一致；原生 release 的 44 通道不变。[不可变 PR16 报告](https://github.com/OpenMixture/OpenMixture/blob/5e360686da38197ee6a12f3f29fd5f20faea2935/docs/evidence/warp-explicit-interpolation/README.zh-CN.md)保留了源码、运行和变化身份。这否定了“像素不变替换”的说法，但不证明每个变化的软件像素在数学上更差。
3. **标量真值有前提。** [26 点精确有理数对照](../evidence/warp-interpolation-reduction/README.zh-CN.md)使用存储采样值和已经舍入的权重。与它一致，不等于位移、邻居选择、完整双线性表达式、上游噪声和最终 PNG 都正确舍入。见证确实绑定两端实际纹理值，但按失败点选取的样本不能建立全局误差界。将一个中间 f32 正确转成 half，也不等于将完整精确表达式正确转成 half。
4. **没有建立普遍编译器缺陷结论。** 核查的 [WGSL 草案](https://github.com/gpuweb/gpuweb/blob/cd910cf650d05481b60bad2b44476caff974962f/wgsl/index.bs) §§15.7.2–15.7.5、§17.5.32 允许算术变化与非融合 fma，其 “correctly rounded” 并不要求普通 f32 操作采用最近偶数舍入。[此前最小乘加见证](../evidence/chromium-arithmetic-reduction/README.zh-CN.md)证明该见证的两个结果都被允许，不是对所有材质操作的规范审计。严格编译与显式 fma 都不是独立数学真值。本次不发送上游 issue。

因此，之前“具体缺陷已修复”的措辞应限于**已测输入上的数值损失得到改善**，不能解释为“证明浏览器违反规范”或“获得兼容批准”。历史报告保持原样，本日期化说明不改写测量结果。

## 为什么微小误差仍会触发失败

half 转换存在舍入分界。两个很接近的 f32 结果如果落在分界两侧，就可能产生相邻 half 值，继而改变 RGBA8。现有整数 half 辅助函数统一的是收到的数值如何转换，不能把不同输入变成同一值。实数误差更小，不代表相对历史基线的变化像素更少。

可用于诊断的分析是：设 `x` 为独立定义的标量结果，`m` 为它到最近 half 舍入分界的距离，`epsilon` 为有依据的上游数值误差界。误差区间完整落在同一舍入区间时，量化结果稳定；跨过分界则不能证明唯一 half 结果，恰在分界的平局另行处理。这是拟议分析，**不是已实现的新门槛，也不允许忽略边界像素**。不能根据目标通过率反推 epsilon。

## 兼容边界与决策规则

| 拟议变化 | 处理方式 |
|---|---|
| 代数等价写法，公共数值承诺不变，全部既有门槛通过 | 正常审查后可作为 v1 实现变化，记录新构建／归档身份。 |
| 实数采样含义不变，但冻结验收像素改变 | 属于有意的数值输出兼容变化，不是透明补丁。任何 golden 操作前必须明确影响并接受审查。当前 PR15/16 属于此类。 |
| 新增强制舍入顺序、量化精度、确定性模式，或改变字段含义／端口／默认值 | 数值或语义契约变化，按架构审查节点版本和迁移政策，不得静默重解释 v1。仅当文档语言需要变化时才涉及顶层格式版本。 |
| 要求所有实现输出逐位一致 | 新产品范围，不由“图确定性”推出；须先定义数值模型、支持环境及性能／打包证据，并审查架构和路线图。 |

不能每变一个字节就自动升级节点版本，也不能认为升级运行时版本就自动允许改变节点含义。已有消费者应保留原始源码／构建／归档和输出，仅 `.mix` 加 plan hash 不足以复现旧像素。这不引入第二渲染器或隐式兼容回退。

有意迁移 golden 与“把测试变绿”的区别在于：先独立定义缺陷和目标数值行为；由预先确定的测试和误差分析支持；披露全部材质变体及消费者影响；保留旧基线、失败和图像；在现有受控更新流程之前取得明确的兼容与视觉决定。只更新软件 golden 也不能认证 Chrome，因为浏览器与同源码原生参照的比较仍是另一道门槛。本次审查既未授权也未执行这些验收操作。

## 推荐的下一项有界任务

**先审计 warp 位移、插值和 half 分界的误差，再提出新的改写或编译策略。** 在比较实现前冻结输入集：现有 23 个字面值、全部既有木材变体、双轴正负方向、端点／中性及近中性位移场、细长和奇数尺寸，以及记录种子的独立保留样本。不要按哪个后端获胜来选择样本或参照。

分别分析：（a）实际 f32 参数／half 输入经位移和邻居选择的误差；（b）固定权重后的插值误差，再单独跟踪传播。记录坐标环绕、精度和舍入假设。参照应标为理想算术或明确的逐阶段舍入模型，不能只称“原生真值”。用同一定义比较原始、仅局部坐标、显式插值三个实现，记录原始误差、邻居变化、量化分界跨越、有限值／范围／接缝及两道不变的材质门槛。标量有理数／区间工具仍是诊断，不成为 CPU 材质执行器。

产出必须能够支持一个范围明确、兼容代价已知的有意数值修正，或说明收益不足以采用。若产品确实需要更广泛的逐位一致，应停止局部写法试错，另立数值模型提案。不启动编译器分叉、不全面替换 fma、不放宽容差、不重置基线。PR15/16 保持草稿，Chrome／Edge 完整材质认证仍待完成。
