# M3 review and M4 entry decision

English | [简体中文](./m3-review.zh-CN.md)

**Reviewed source:** `e9dd03b` (PR-010), 2026-09-08. All three materials have user acceptance and passing local Metal/pinned SwiftShader evidence. The six questions required [after PR-010](../INITIAL_PRS.md#after-pr-010) are answered below. The resulting [M4 implementation train](../M4_PRS.md) is planned; its runtime changes are not implemented by this review.

Remote clean-checkout/Linux CI remains deferred at the user's request. Local material acceptance does not close those outstanding platform gates or authorize a release. The catalog stays at eleven nodes; this review does not relax the thirteenth-node stop rule.

## 1. Are the three materials acceptable to a human reviewer?

**Yes, for the current accepted appearance targets.** The user accepted [ceramic](../fixtures/materials/glazed-ceramic/reports/human-review.json), [leather](../fixtures/materials/leather/reports/human-review.json), and [wood](../fixtures/materials/wood/reports/human-review.json) after their controlled PBR comparisons. These decisions are bound to the recorded manifests and PBR evidence; they are not inferred from machine scores. Earlier PBR captures retain their historical pending labels and do not claim to perform human acceptance themselves.

The [acceptance receipt](./reviews/m3/acceptance.json) verifies those bindings and consolidates the final local reports: eleven 1K cases across the three materials, four channels each, on both policies. Software comparisons are exact. Hardware uses each material's declared tolerance; wood's documented maximum of two byte levels and limited changed-pixel ratio remains unchanged. Structural range, seams, spatial/directional variation, parameter causality and height/normal relationships retain their existing gates. The accepted source and pixels have not been regenerated by this review.

This establishes the three scoped material targets, not photorealism across arbitrary scenes or a broader node vocabulary.

## 2. Can another developer understand the public `.mix` vocabulary?

**Yes, with the public guides; independent usability testing is still absent.** The [format](./file-format.md), [eleven node contracts](./node-contracts.md), and material-owned documents specify versions, typed ports, parameter defaults/ranges, explicit seeds, coordinate conventions, tiling limits, exposed overrides and output encodings. Validation rejects unsupported data instead of repairing it. Public `BUILT_INS` and `node_contract` already expose the serializable catalog, so a second catalog/schema API is unnecessary.

The [independent Cargo probe](./reviews/m3/native-consumer/README.md) owns its input and successfully decodes, validates, overrides and compiles it using public imports. This is developer evidence, not a study with unfamiliar users. Two stale Rustdoc statements remain: the core introduction says six contracts and `MaterialDocument::validate` describes compilation as future work. PR-011 corrects them and replaces repository-relative documentation examples with consumer-safe examples.

## 3. Can diagnostics guide graph and GPU setup repairs?

**JSON diagnostics and `doctor` provide the necessary context; human output has a specific defect.** The [sixteen CPU probes](./reviews/m3/diagnostics/README.md) preserve raw stdout, stderr and exit codes for help/usage, malformed/invalid graphs, overrides, limits, I/O and explicit disabled-GPU acquisition. Graph/request failures return exit `2`; I/O/acquisition failures return `1`. JSON retains node/port/parameter identifiers, measured evidence and suggestions. [Recorded healthy-adapter evidence](../fixtures/materials/wood/reports/README.md) covers actual GPU setup separately; disabled-backend probes do not simulate a device failure.

For a warp without its required input, human `validate` identifies `displacement`, while human `inspect --plan` and `render` omit the port. Their JSON still preserves it. PR-012 must make all three human reporters retain that context and test the same invalid fixture across both output modes. This gap is not silently treated as SDK readiness.

Runtime device loss and out-of-memory classification remain M4 work. Existing stage-specific errors preserve driver evidence, but do not yet expose a stable distinction for these two failure reasons. PR-013 owns that contract.

## 4. Does 1K performance support interactive consumers?

**It supports a debounced preview workflow on the measured host; continuous frame-rate interaction is not established.** The review measured an optimized CLI built with `--release --locked --all-features`, sequential fresh processes, 1024×1024 output and three trials per workload. Every requested PNG was decoded after timing and compared to the accepted baseline. Metal outputs passed their tolerances; the SwiftShader wood outputs matched exactly. Full commands, binary/source hashes, adapter reports and raw output are in the [performance evidence](./reviews/m3/README.md).

| Adapter / workload | Passes | Complete CLI median ms | Observed min–max ms | Renderer median ms |
|---|---:|---:|---:|---:|
| Apple M5 / Metal, ceramic, four channels | 8 | 62.6 | 60.0–237.0 | 32.7 |
| Apple M5 / Metal, leather, four channels | 5 | 714.4 | 710.5–896.6 | 41.5 |
| Apple M5 / Metal, wood, four channels | 8 | 408.2 | 401.5–604.3 | 38.7 |
| Apple M5 / Metal, wood coarse grain, four channels | 8 | 340.5 | 338.9–361.6 | 41.3 |
| Apple M5 / Metal, wood, baseColor only | 6 | 160.6 | 158.6–162.7 | 19.9 |
| Pinned SwiftShader / Vulkan, wood, four channels | 8 | 623.9 | 618.6–633.2 | 232.9 |

Complete CLI time includes process launch/exit, decode/compile, GPU acquisition, execution, readback, PNG encoding/writes and JSON. `Renderer` time excludes CLI encoding and GPU context acquisition; it includes CPU preparation/waits and readback conversion. These are wall times, not GPU timestamps. Column medians are calculated independently. The first ceramic/leather/wood Metal trials include 177–204 ms of pipeline creation; no warmup or slow trial was discarded. Processes have fresh Mixture caches, while OS/driver caches may be warm. Three samples on one machine are not p95 estimates, a portable SLO or a promise about every first launch.

Minimal `--version` calls took a median 3.1 ms on the Metal run (6.3 ms during the software run). This is a baseline invocation proxy, not an isolated render-startup measurement. It gives no evidence that process startup requires N-API, a daemon or IPC. The large gap between complete CLI and renderer time for leather/wood directs the next measurement toward CLI setup/encoding costs and a public Rust consumer returning owned pixels. It does not by itself isolate PNG encoding or justify a shader/resource optimizer.

PR-011 therefore begins with the existing public Rust path. A Node.js consumer, if later needed, starts by spawning the built CLI. PR-014 adds request generations and stale-result rejection so slow completed work cannot replace the newest preview. Requesting only needed channels already reduces work, as the six-pass wood result demonstrates. No new performance threshold is invented by this review.

## 5. Is 2K memory bounded by a simple lifetime model?

**Yes, for the measured workload and descriptor budget.** Both retained [Metal](../fixtures/materials/wood/reports/2k/metal/trace.json) and [SwiftShader](../fixtures/materials/wood/reports/2k/software/trace.json) traces select `wood/default` from eleven candidates by estimated peak memory, not elapsed time. At 2048×2048 with four channels and eight passes:

| Quantity | Bytes |
|---|---:|
| Pass textures | 268,435,456 |
| Uniform buffers | 224 |
| One live staging buffer | 33,554,432 |
| Peak live descriptors, estimated and allocated | 301,990,112 (about 288 MiB) |
| Allowed peak | 536,870,912 (512 MiB) |
| Cumulative allocation and released bytes | 402,653,408 |
| Live bytes after render / reused bytes | 0 / 0 |

Keeping all pass textures/uniforms until the end, with one sequential readback buffer, is sufficient. No last-consumer release, pool or texture reuse is justified by this evidence. The count excludes driver allocations, pipelines/bind groups and CPU output buffers; explicit destroy/drop does not prove immediate OS physical-memory reclamation. The budget is per render, not an aggregate cap across concurrent consumers. These development-build 2K timings are not reused as release-interaction measurements.

## 6. Which API does an independent native consumer need?

**The existing public path is sufficient for the initial consumer.** It needs `MaterialDocument::decode`, validation, `CompileRequest`/`compile`, explicit `GpuContext::request`, and `Renderer::render`, plus typed diagnostics. The result already provides owned RGBA8 pixels, size, channel kind/encoding and connected/default provenance, plan hash, adapter, passes, timings, allocation and pipeline-cache evidence. Core owns semantics; wgpu owns pixels; the consumer owns display/export and request freshness.

The separate [Cargo fixture](./reviews/m3/native-consumer/README.md) executes CPU decode/validate/override/two-channel compilation and an invalid override. It compiles the GPU request/render/result/drop path and native `Send` bounds. **It has not executed GPU rendering and uses source path dependencies, so it is not package-consumer acceptance.** PR-011 must execute the public path on explicitly selected adapters and verify pixels remain usable after dropping the renderer. PR-015 must prove packaged sources work without repository-relative assets.

Before promising compatibility, M4 must review public raw-wgpu getters, fix CLI diagnostic omissions, define device-loss/OOM behavior, establish stale-result handling, and test existing bounded cache lifetime. These needs produce [PR-011 through PR-015](../M4_PRS.md); they do not require a new executor, a new runtime crate, bindings or an editor.
