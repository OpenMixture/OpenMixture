# 证据保留策略

[English](./evidence-policy.md) | 简体中文

本策略适用于 M4.1 起新增的证据，在保持验收可审查的同时，避免将每次成功运行的完整副本都纳入 Git。它不改写历史执行结果，不改变材质门槛，也不添加运行时或验证框架。[发布状态](./release.zh-CN.md)、[兼容性](./compatibility.zh-CN.md)和[原生 SDK 契约](./native-sdk.zh-CN.md)继续定义产品就绪状态与公开行为。

## 历史记录与当前指引

保留可执行的金图／清单及支持当前验收的来源绑定内容。维护者确定方向后，可以从当前目录移除已替代研究、被拒绝的实验和重复诊断；Git 历史及已关闭 PR 保留原始结果。同时移除过时导航和执行依赖。保留的记录如需旧文件，应链接具体历史提交。不得将失败改写为成功、修改绑定回执，或删除当前验证仍必需的输入。原始 `mixture-greenfield-docs/` 文档包属于独立参考资料。

当前导航与说明指南可以同步更新中英文，指向较新的已接受版本，并解释哪些旧表述属于历史事实。若需纠正历史结论，应新增带日期的记录并链接原文；不得替换原始结果，也不得声称旧运行测试了新源码。[远端 CI 记录](./evidence/remote-ci/README.zh-CN.md)分别保留了失败与已接受的运行。

## 新证据应保留什么

按证据用途分类，不仅按扩展名或体积分类。

| 证据 | 新增内容的保留方式 |
|---|---|
| 可执行的验收输入 | 源 `.mix` 文件、验收 schema／契约、参数变体、预期 PNG 与清单、聚焦夹具和复现脚本／命令保留在 Git，使检出仓库后仍可使用。 |
| 人工验收与视觉决策 | 决策回执及其绑定的对照图片／报告保留在 Git，包括相关前后对照与差异证据。小型摘要或哈希不能替代实际被接受的图片。保留用于说明容差或语义决策依据的失败证据。 |
| 已接受的里程碑或材质结果 | Git 保留绑定源码的简明摘要，包含关键机器测量、门槛结果、限制和人工决策引用，并保留检查这些结论所需的实际支撑内容。 |
| 普通重复运行 | 完整 stdout／stderr、重复 JSON 报告、未选中的候选、重复 PNG 和大型常规跟踪保留在被忽略的本地输出目录或有限保留期的 CI artifacts 中。不将每次成功运行都复制进 Git。如果其中内容成为验收或失败决策的证据，应提升保留必要子集。 |
| 构建与暂存数据 | 编译产物和 SwiftShader 构建保留在被忽略的目录或缓存中。验证器可删除成功运行自有的包解压目录，但应在清理前保留其回执及必要归档证据。缓存不是验收证据。 |

对于新接受的视觉变更，人工回执引用的全部文件必须保持可用，并绑定已接受的字节。普通运行的完整输出若有意仅作临时保留，应在摘要中说明。复现说明可以生成新运行，但不能恢复或认证已经不可用的原始 artifact。

## 已接受运行的最小摘要

使用小型结构化记录，必要时附上成对的人类说明文档。这是保留要求，不是新实现的报告 schema 或命令。既有报告格式仍具权威性；应标明其 schema 版本，对不适用或不可用的字段明确说明，而不是编造值。

- **源码：** 完整被测提交 SHA、工作树是否干净；若包含未提交工作，还需相关源码／输入哈希；复现结果所需的工具链、锁文件、shader、夹具、验收契约和基准身份。不得将后来的文档提交描述为被测提交。
- **运行：** 时间戳与时区、本地或 CI 来源、可用时的运行 ID 与 attempt、workflow／job 身份、命令及相关选项／环境、各必需门槛的完成状态与结果。失败、跳过或未完成的工作必须与成功区分。
- **执行：** 主机 OS／架构、请求的适配器策略、实际适配器／后端、适用时已验证的软件源码版本、分辨率、通道、变体／覆盖、计划哈希，以及具有决定性的比较／资源测量。不得从 CPU 检查推断硬件 GPU 覆盖。
- **验收：** 结果与范围、已知限制、选定的失败证据，以及必要时人工决策和所审阅内容的引用／摘要。机器检查和 `golden update --accept` 不代表人工审阅。
- **产物：** 相对路径或获取位置、归档／artifact 名称与 ID、内容摘要和体积、可用时的创建／到期信息，以及验证解压后包所需的支撑文件身份。包验收还需保留归档／源码／锁身份，以及外层验证器的来源与消费结果。
- **保留：** 哪些内容留在 Git、哪些仅临时保留、持久归档位置及负责维护者；若声称持久保留，还需记录最近一次成功获取与完整性检查。明确说明不可用的原始内容及由此造成的审计限制。

计划哈希标识规范化语义，不标识原始源码写法、实现／shader 字节、GPU 像素、包内容或请求新鲜度。单独的提交 SHA 无法标识脏工作树。artifact 摘要可验证取回的字节，但不会让这些字节持续可用。应保持[兼容性记录](./compatibility.zh-CN.md)与[包验证方法](./package-consumption.zh-CN.md)中的这些区别。

## CI 到期与持久保留

[CPU workflow](../.github/workflows/ci.yml) 和 [GPU workflow](../.github/workflows/gpu-smoke.yml) 通过 CI artifacts 保留生成的证据。这些 artifacts 有限期保留。对已接受的运行，应在可用时记录配置的保留期限和返回的到期时间；不得承诺运行 URL 可以永久下载。源码和驱动缓存也可能独立失效。

记录验收的维护者负责其保留决策。在依赖外部持久归档前，该维护者必须选择可访问的位置，明确保留责任人／策略，存入所需证据包，再取回并验证其摘要与必需内容，然后记录检查结果。复制证据包时保留原始运行／源码身份。持久副本与重新执行或发布版本是不同的事项。

没有可用的持久归档时，应在 Git 保留最低必要的验收内容，并说明哪些完整日志或附带输出会到期。如果预期审计需要原始完整包，就保留该包或缩小所声明的范围；仅靠哈希与运行 ID，无法支撑完整运行可长期审计的声明。到期不会将先前记录的通过变成失败，但会限制日后检查原始运行的能力，必须如实记录这一限制。

维护者选定的[历史证据 Release](./evidence/archives/README.zh-CN.md)按需存储明确列出的 ALPHA-04、M5-05 和早期运行快照。这是完整历史附件的限定例外，不适用于当前可执行 golden 或人工验收绑定图像。决策记录、关键失败／校准证据、具名评审图、标识和取回清单仍保留在 Git。保留原回执，以独立映射描述迁移路径。从当前目录移除附件前，必须下载并验证归档及全部成员。仓库维护者负责无计划到期的保留，资产不得原位替换。不引入自动保全任务或产品发布。已替代研究可按上述当前指引规则精简。

## 保持验证与职责边界

[基准工作流](./material-goldens.zh-CN.md)继续区分渲染、视觉检查、受保护的基准安装和人工验收。候选完整性覆盖运行时／shader／工具源码、输入、原基准和已审阅产物。尤其是[候选输入哈希](../xtask/src/golden/files.rs)包含 `xtask/src`：即使像素不变，工具改动也可能使尚未接受的候选失效。应重新运行并审阅，绝不能重写其哈希来绕过保护。

本地文档链接仍须有效，人工验收绑定仍须指向可用内容。[链接检查器](../xtask/src/links.rs)排除外部 URL，因此链接检查通过不代表 artifact 可取回。保留[隔离包验证](./package-consumption.zh-CN.md)所需的源夹具与独立消费者输入；历史证据不是包运行时依赖。

保留策略变更不得削弱失败传播、源码／归档检查、材质比较或独立消费者检查。文件体积本身不是拆分 `xtask`、添加 crate 或引入通用证据框架的理由。任何后续工具改动都应依照[开发工作流](./development.zh-CN.md)，运行所属命令的聚焦检查和 `cargo xtask check`。

## 增长防护

`cargo xtask evidence` 包含在 `cargo xtask check` 中，因此每项必需 CPU 检查都会执行。它对受跟踪文件执行上表规则（[实现](../xtask/src/evidence.rs)）：

- 证据区域（`docs/evidence/`、`docs/reviews/` 及 `fixtures/**/reports/`）拒绝原始 `.log`、`.stdout`、`.stderr` 输出，`.tar.gz`、`.tgz`、`.zip` 归档，以及单次运行的 `cli-<pid>-<time>` 目录。
- 任何超过 4 MiB 的受跟踪文件都会被拒绝，无论位于何处。

[保留例外](./evidence/retention-exceptions.txt)按目录列出有意保留的此类文件数量。防护加入时已有的条目记录其之前的内容。防护会报告过期计数，因此清理记录后列表随之缩短。仍可将失败日志或大型已接受二进制文件保留为证据：在同一 PR 中新增或调高该目录的条目，并说明为何必须保留在 Git 中。防护只读取 Git 索引，不会删除、移动或改写证据；删除文件也不会缩小 Git 历史。

不改写已有历史。2026-09-24 实测，全部远端分支的压缩对象约 234 MiB：约 213 MiB 仍在当前 `main` 目录中（约 160 MiB PNG 和一个 50 MiB 归档），仅存在于历史中的内容只有约 21 MiB；原始日志和单次运行输出压缩后合计不到 1 MiB。改写历史会改变回执、集成记录和 PR 引用的全部提交身份，并需强推所有分支，而节省有限。只有在维护者单独决定时才重新考虑，例如与将大型已接受二进制文件迁移到持久外部存储一并进行。

## 准确描述验证范围

下列类别描述证据覆盖，不设立新的支持等级或服务保证。精确的已接受版本、主机、结果与限制仍见[发布状态](./release.zh-CN.md)及其链接记录。

| 类别 | 当前证据边界 |
|---|---|
| 持续 CI 验证 | Linux／macOS／Windows CPU 检查，以及配置的 Linux 固定 SwiftShader Vulkan GPU／材质／包／跟踪工作负载。存在 workflow 不等于未测试版本已经通过。 |
| 已记录的开发机验证 | macOS 上已记录的 Apple M5／Metal 和本地固定 SwiftShader 运行。注明主机、日期、源码与工作负载；不得将一台主机提升为普遍 Metal 支持或 Tier 1 承诺。 |
| 尚无验收记录的原生硬件 | 已记录矩阵之外的其他 Metal 硬件、硬件 Vulkan 和 Windows／DX12 配置。暴露后端选项不等于认证这些设备。 |
| 浏览器工作尚未开始 | M4.1 没有已完成的 Browser WebGPU 实现或已接受的浏览器矩阵。拟议的浏览器 CI 环境不是当前证据。 |

本策略不扩大平台支持，不启动 M5，不发布软件包，不改变基准，也不重新裁定已接受的历史决策。
